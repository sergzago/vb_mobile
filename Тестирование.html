Ключевая особенность реализации (server/src/services/scoreboardService.js): в классическом режиме счёт по сетам хранится в полях home_fouls / away_fouls (поля home_sets/away_sets ведутся только в пляжном режиме). Сет засчитывается при наборе очков через POST /score (_classicSetWon → _applyClassicSetWin), а также по текущему счёту при переключении партии (POST /new-set и POST /period). После серии исправлений: PATCH не принимает home_score/away_score (400), -1 при pending_new_set откатывает засчитанную партию, +1 при pending_new_set игнорируется, а операции чтения-записи по одной игре сериализованы (in-process lock) — поведение и API согласованы с фронтендом (js/mobile.js).

Группа 2 — Репродукция «счёт по партиям не переключился»: 33/33 PASS (все дефекты исправлены)

R1. Запись счёта в обход POST /score (через PATCH) — ИСПРАВЛЕНО (ранее REPRODUCED)

  • PATCH {home_score:25, away_score:23} теперь → 400 (home_score/away_score нельзя менять через PATCH: очки принимаются только через POST /api/scoreboard/{game_id}/score); счёт остаётся 0:0. PATCH с одним away_score — тоже 400.
  • PATCH остальных разрешённых полей (tournament_name, команды, цвета, period_count, флаги) — по-прежнему 200 и применяется.
  • Обход детекции закрыт; штатный путь через /score засчитывает партию как раньше (1:0, pending_new_set=true).
  • Изменение: routes/scoreboard.js — ранний ответ 400 при наличии home_score/away_score в теле PATCH; эти поля убраны из allowedFields. Проверки R1.0–R1.7 — PASS, V3.3b — PASS.

R2. Режим unlimited_score + POST /new-set — ИСПРАВЛЕНО (ранее REPRODUCED)

  • При unlimited_score=true автоопределение победы в сете по-прежнему отключено (25:23 → сеты 0:0) — ожидаемое поведение режима.
  • POST /new-set теперь засчитывает партию по текущему счёту: после 25:23 → сеты 1:0, set_history=[{25,23}], период=2, очки 0:0, применена смена сторон (home_side=right).
  • Вторая партия (25:20) + new-set → сеты 2:0, classic_match_finished=true, результат "2:0" сохранён в /api/matches. new-set и period теперь эквивалентны.
  • Изменение: newSet() разделён на _newSetLocked (проверка и запуск) и _applyNewSet (смена сета), логика засчитывания — _setWonByCurrentScore/_countCurrentSet (аналог updatePeriod). Проверки R2.0–R2.11 — PASS.

R3. Откат «-1» после победы в сете → двойное засчитывание — ИСПРАВЛЕНО (ранее REPRODUCED, самый серьёзный дефект)

  1. Партия выиграна 25:23 → сеты 1:0, pending_new_set=true.
  2. POST /score delta:-1 → очки откатываются до 24:23 и счёт по сетам возвращается к 0:0, set_history очищается, pending_new_set/next_period/pending-стороны сбрасываются (порт revert-логики js/mobile.js).
  3. Повторный +1 (снова 25:23) засчитывает партию ровно один раз → 1:0, classic_match_finished=false.
  4. В /api/matches ложной записи "2:0" нет.
  • Изменение: _buildSetRevertUpdate(data, team) и ветка отката в _updateScoreLocked; guard-ы !data.pending_new_set в _handleClassicScore/_handleBeachScore. Проверки R3.0–R3.9 — PASS, в пляжном режиме — B1.10–B1.12.

R4. Параллельные запросы — ИСПРАВЛЕНО (ранее REPRODUCED, единственный FAIL первого прогона)

  • 8 одновременных POST /score (5 × home, 3 × away) → home_score=5, away_score=3, ошибок нет (до правок: 2 очка из 5 и четыре HTTP 500 с autocancelled).
  • 2 одновременных +1 при счёте 24:23 → партия засчитана один раз (1:0), счёт 25:23 — без двойного засчёта и без «лишнего» очка.
  • Отдельно: +1 при pending_new_set игнорируется (200, счёт не меняется) — на фронтенде кнопки счёта в этот момент заблокированы (js/mobile.js:1024), а API устойчив к повторным/параллельным запросам.
  • Изменение: client.autoCancellation(false) при создании PocketBase-клиента (config/db.js, routes/auth.js) и сериализация read-modify-write по game_id (_gameLocks/_withGameLock, применена к updateScore, newSet, updatePeriod). Проверки R4.0–R4.5 — PASS.

Ответ на основной вопрос: в штатном сценарии (набор очков через POST /score) счёт по сетам корректно меняется при окончании каждой партии и при окончании игры (1:1 → 2:1, classic_match_finished=true, матч сохранён с overall_score="2:1"). Ранее «счёт по партиям не переключался» в четырёх ситуациях: (a) запись счёта в обход /score, (b) переключение партии через new-set при unlimited_score, (c) откат очков -1 после победы в сете, (d) параллельные запросы. Все четыре причины устранены — повторный прогон: 130/130 PASS (группа 1 — 41/41, группа 1b — 17/17, группа 2 — 33/33, валидация — 17/17, очистка — 10/10).
